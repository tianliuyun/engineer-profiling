# 伙伴工程师能力画像与培训推荐系统

> **从"全员一锅端"到"精准推"：让每个工程师都有自己的能力画像和培训路线**
> 技术方向：文本分类 · 聚类分析 · 个性化推荐 ｜ 全本地规则 + 统计 + 无监督实现，**离线可用、秒级跑通**

一款面向 to B 交付业务的伙伴/合作工程师能力管理工具。从几十上百个工程师的历史工单、培训、认证数据出发，自动为每个人构建**能力画像**，把团队按技能**聚成能力群组**，再为每人**精准推荐个性化培训**，让培训资源从"大锅饭"变成"精准赋能"。

---

## 一、项目背景

### 业务痛点
企业通常管理 **50+ 位伙伴工程师**，过去的管理方式严重依赖经验：

| 痛点 | 现状 | 代价 |
|---|---|---|
| 能力不清 | 不知道谁擅长什么、谁缺什么 | 派单靠感觉，首次解决率低 |
| 培训大锅饭 | 全员同一套课，讲的内容有人嫌简单有人嫌难 | 培训效率低，资源浪费 |
| 认证通过率低 | 不知道该针对性补什么 | 认证通过率仅 ~30% |
| 成长无路径 | 工程师不知道自己缺什么、下一步学什么 | 人员流失、积极性低 |

### 本项目目标
1. 每个工程师一张**能力画像**（5 产品线 × 3 难度档）
2. 团队自动聚成**技能群组**，培训**分班精准授课**
3. 为每人生成**个性化培训推荐**（含补课优先级与理由）
4. 目标：**认证通过率 30% → 60%**，培训针对性从"全员覆盖"升级为"精准推"

### 技术选型与取舍
- **不依赖真实 LLM API**：全部用本地关键词词典做文本分类 + sklearn 无监督聚类 + 自研加权排序，保证离线可用、可复现、每一步都可解释。
- **字典打标 vs BERT 微调**：数据量有限的伙伴环境，词典分类够用且零标注成本；等数据积累到万级再升级 embedding 分类（见文末 FAQ Q2）。
- **K-Means vs DBSCAN**：伙伴团队规模有限、希望固定分成 N 个培训班，K-Means 简单可控；若后续要自动识别"独立能力孤岛"可换 DBSCAN。

## 三、量化指标

| 指标 | 含义 | 本项目表现 |
|---|---|---|
| 画像维度 | 每个工程师的能力粒度 | **5 产品线 × 3 难度档 = 15 维能力矩阵** |
| 多路信号 | 画像融合的数据来源 | 工单 / 培训 / 认证 **3 路信号** |
| 聚类区分度 | 群组能否拉开差距 | 实测 3 群组平均综合分 **0.438 / 0.564 / 0.627** 呈梯度 |
| 推荐准确率 | Top1 是否命中短板产品线 | 工程化设计短板优先，**可复现的确定性排序** |
| 冷启动策略 | 无历史数据如何处理 | 规则 + 基准分打底，随数据自动修正 |
| 单测 | 可回归验证的行为 | **15/15 pytest 全部通过**（秒级） |

**业务价值换算**（演示数据的业务侧效果）：
- 培训从"全员一套课" → "按群组分班 + 每人 3 门优先课"，**覆盖全部短板产品线**
- 认证通过率目标从 30% → 60%（补齐短板后的预期提升，作为团队 KPI 追踪）

## 四、典型业务效果

面向 50+ 伙伴工程师的交付能力管理与培训运营，过去能力评估靠老师傅经验、培训全员一锅端，认证通过率仅 30%。使用本系统：

- 从**历史工单 / 培训记录 / 认证考试**三维度建模，用**文本分类**为每条工单自动打「产品线 + 难度」标签，形成每人 15 维能力画像；
- 用**聚类分析**（K-Means）把团队按能力向量聚成可命名的技能群组，培训从"全员"变为"分班"（实测 3 群组均分梯度 0.44 → 0.63）；
- **短板优先的召回 + 排序推荐**：每个工程师输出 Top3 培训课 + 中文推荐理由；
- **冷启动兜底**：无历史数据的新人用规则 + 基准分打底，随数据积累逐步修正画像；
- 认证通过率目标从 30% 提升到 60%（团队 KPI 追踪），全程 pytest 15 个单测保障、离线可复现。

## 五、设计问答（FAQ）

### Q1：冷启动怎么解决？新来的工程师没有历史数据怎么办？
**答**：设计了两层兜底。① 规则 + 基准分：没有任何产品线记录时，画像回落到一个稳定的基准分（`COLD_START_BASE = 0.35`），保证系统永远有输出、不和历史库冲突；② 随数据演进：一旦有了真实工单/培训/认证记录，就用 `样本量加权` 逐步替换基准分——`得分 = α·真实能力 + (1-α)·先验`，α 随样本量增大而逼近 1。这跟推荐系统对新用户用"全局均值+冷启动池"打底的思路一致。

### Q2：为什么用词典文本分类，不用 BERT / LLM？
**答**：这是个取舍题。当前场景数据量小、产品线是有限封闭集（5 个）、单机离线跑，词典打分 + 规则兜底**零标注成本、可解释、毫秒级**，足够满足业务。但我会讲清楚升级路径：当工单量积累到万级、产品线膨胀到 50+，会换 embedding（如 BGE）做语义分类，或者对难样本做 LLM 标注迭代，再到全量微调。**先保证当前可落地，再谈扩展**。

### Q3：聚类为什么用 K-Means？换 DBSCAN 会怎样？
**答**：企业需求是"稳定分成 N 个培训班、人数好预估、每年可复现"，K-Means 的 `n_clusters` 可控、解释清晰、确定性输出；标准化后再聚类避免量纲偏差。缺点是要求球形分布、对离群点敏感。如果后续要自动发现"能力孤岛"（比如某个冷门产品只有 1 个人会），会引入 DBSCAN 靠密度自动定簇——但那是二期需求，一期稳定分班更重要。

### Q4：画像分数够公平吗？会不会"处理过 2 单就判满分"？
**答**：不会，专门做了**样本量正则化**。所有产品线得分都带 `min_samples` 先验回调——样本越少，得分越向基准分靠拢，避免小样本幸存者偏差；并有冷启动统计模块监控"存在空洞的工程师"，方便运营介入补数据。这是做个好评判标准的关键细节。

### Q5：你怎么验证推荐是"准"的？
**答**：工程化手段是**确定性排序 + 单测**：推荐顺序由「短板程度 × 难度适配」这个可解释的排序函数决定，并写了单测断言"短板最大的产品线必须排第一"。业务层我会配 A/B 实验：随机一半按推荐补课、一半继续大锅饭，追踪三个月后的认证通过率差和首次解决率差，用数据说话。

## 快速开始

```bash
# 1. 创建虚拟环境并安装依赖（仅 numpy + scikit-learn，需网络装一次）
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt

# 2. 运行全部单测（15 个，秒级通过，离线可跑）
pytest -q

# 3. 一键演示完整链路（画像 → 聚类 → 推荐 → 报告）
python examples/demo.py
# 报告导出到 outputs/report.json
```

### 依赖
- **Python ≥ 3.9**
- numpy、scikit-learn（仅用于聚类）、pytest（开发/测试）
